# 实测数据

这里只放实际跑出来的数字，每一项都注明在哪台机器、用什么方式测的。样本量小的地方直接写明，不把它当成基准。

测试机器都是 GitHub Actions 的免费托管机器：Windows 和 Linux 是 4 核纯 CPU 的虚拟机，和一台普通笔记本相当；macOS 是 3 核的 Apple Silicon 虚拟机，它的 GPU（Metal）速度每次运行差别很大，所以 macOS 的耗时只作参考。真实笔记本上的数字要自己测：`npx electron . --selftest --real` 会打印同样格式的报告。

## 1. 结论先说

| | 原版 0.8B，快速定位 | 原版 0.8B，精确定位 | 0.8B + 指针适配器（LoRA） |
|---|---|---|---|
| 怎么得到位置 | 回答后在同一段对话里追问 | 回答后把截图放大，单独再问一次 | 回答的同时输出，**一趟完成** |
| 8 题里指对几题 | **0**（三个系统、每次都是） | 4–6 | 4–5 |
| 每题耗时（Windows / Linux，4 核 CPU） | 7–10 秒 / 8–10 秒 | 21–26 秒 / 17–32 秒 | **7.1 秒 / 6.6 秒** |

一句话：**适配器让小模型用一趟推理做到了原来要两趟、三倍时间才能做到的事**；它没有让模型在这张测试页上指得比"精确定位"更准。

"指对"的标准：AI 给出的点落在问题所问的那个界面元素的范围内（外扩 6 像素）。

应用的选择：有适配器文件就用一趟模式；没有就用精确定位。快速定位保留为一个选项（`settings.json` 里 `local.locate: "fast"`），但它在原版模型上不可用。

## 2. 原版模型：定位方式的对比

**怎么测的**：应用自己执行 `--setup` 装好运行时和默认模型，再用 `--selftest --real` 启动本地模型，对同一个测试页面（[`test/e2e/stage.html`](../test/e2e/stage.html)）问 8 个问题，每种配置各问一遍。配置：Qwen3.5-0.8B，Q4_K_M 量化，llama.cpp b12110，上下文 4096，没有适配器。

来源：CI 第 9 次运行（2026-11-13）。每格是"答对题数 / 指对题数，首字耗时，每题总耗时（中位数）"。

| 配置 | Windows x64（4 核，纯 CPU） | Ubuntu x64（4 核，纯 CPU） |
|---|---|---|
| 精确定位，放大到 52 万像素（**默认**，同一配置跑了两遍） | 7 / 6，3.2 秒，21.1 秒<br>7 / 4，3.2 秒，26.4 秒 | 8 / 5，6.1 秒，31.7 秒<br>5 / 6，6.1 秒，30.9 秒 |
| 精确定位，放大到 26 万像素 | 7 / 2，3.2 秒，13.4 秒 | 7 / 2，6.1 秒，19.1 秒 |
| 精确定位，放大到 13 万像素 | 6 / 3，3.1 秒，8.4 秒 | 5 / 2，6.1 秒，15.1 秒 |
| 快速定位（同一对话里追问） | 6 / **0**，3.2 秒，6.6 秒 | 5 / **0**，6.0 秒，10.0 秒 |

macOS（Metal 虚拟机）只跑了默认配置：8 / 6，首字 5.2 秒，每题 33.8 秒。

读法：

- **首字 3–6 秒**，回答本身 4–7 秒就出完；剩下的时间全花在定位上。所以用户先看到回答，AI 光标晚十几秒才飞过去。
- **放大得越小越快，但越不准**。52 万像素是这个模型能指准的下限附近。
- **同一配置跑两遍，结果差 1–2 题**。8 道题的样本只能看出"0 和 5 的差别"，看不出"5 和 6 的差别"。
- 更早的一次运行（CI 第 8 次）试过让运行时把小截图放大到至少 256 / 512 / 1024 个图像 token 再做快速定位：8 题里分别指对 0、0–1、1–2 题，首字却慢到 4–52 秒。问题不在分辨率，而在这个小模型不会在多轮对话里回头定位。

内存（`llama-server` 进程的常驻内存，问完 8 题之后）：Windows 1.1–1.9 GB，Linux 1.5–2.0 GB，macOS 2.3 GB（Metal 把显存也算在统一内存里）。加载后空闲时约 1.04 GB。

## 3. 指针适配器（LoRA）

### 3.1 训练后的离线评测（全精度模型，GPU）

来源：[`train/results/eval.json`](../train/results/eval.json)。每个划分 120 条，都是训练时没见过的样本；"未见类型"连界面的种类（菜单、文件列表、工具栏）都没在训练里出现过。两列用的是同一个"一趟输出回答和坐标"的提示词。

| | 原版 0.8B | 加适配器 |
|---|---|---|
| **未见类型**：点落在正确元素内 | 10.0% | **72.5%** |
| 　其中 菜单 / 文件列表 / 工具栏 | 41.7% / 0% / 11.1% | 91.7% / 69.2% / 61.1% |
| 未见类型：回答里说出了正确的那一项 | 35.8% | 93.3% |
| **验证集**（见过的类型）：点落在正确元素内 | 5.0% | **94.2%** |
| 　其中 对话框 / 价格 / 表格 / 设置 / 代码 / 表单 | 3.7% / 0% / 0% / 0% / 15.4% / 16.7% | 88.9% / 100% / 85.7% / 100% / 100% / 100% |
| 回答里带了坐标 | 55–78% | 100% |

原版模型被要求"一趟同时回答并给坐标"时，要么不给坐标，要么给一个固定的猜测值（多次出现 `[300, 150]`），所以它的命中率接近于零。这不代表原版模型不会定位（第 2 节的精确定位能指对一半以上），只说明它做不到一趟完成。

这些数字的边界：数据全部是程序合成的界面，回答是模板句。72.5% 说明换一种没见过的界面版式它大体还行，不说明它在任意真实应用上都有这个水平。

### 3.2 在应用里的实测（量化模型，纯 CPU）

应用里实际跑的不是 3.1 节那个全精度模型，而是 Q4_K_M 量化的模型加上 f16 的适配器，在 `llama-server` 里纯 CPU 运行。用第 2 节同样的 8 道题、同一台机器、同一次运行里对比。

来源：CI 第 11 次运行（2026-11-13）。每格是"答对题数 / 指对题数，首字耗时，每题总耗时（中位数）"。

| 配置 | Windows x64（4 核） | Ubuntu x64（4 核） | macOS arm64（Metal 虚拟机） |
|---|---|---|---|
| **带适配器，一趟**（有适配器时的默认） | 6 / 4，3.6 秒，**7.1 秒** | 7 / 5，3.1 秒，**6.6 秒** | 7 / 5，2.6 秒，11.1 秒 |
| 原版，精确定位（没有适配器时的默认） | 7 / 5，3.4 秒，24.8 秒 | 6 / 4，2.7 秒，16.8 秒 | 上一次运行：8 / 6，5.2 秒，33.8 秒 |
| 原版，快速定位 | 6 / 0，3.5 秒，10.4 秒 | 5 / 0，2.7 秒，8.1 秒 | 没有测 |

读法：

- **耗时降到三分之一左右**（Windows 24.8 → 7.1 秒，Linux 16.8 → 6.6 秒），因为不再有第二趟。AI 光标和回答同时到。
- **指对的题数和精确定位相当**（4–5 题对 4–5 题），远好于同样快的"快速定位"（0 题）。8 道题的样本分辨不出 4 和 5 的差别。
- 应用里看到的会比这个数字好一点：应用会把模型给的点吸附到附近的界面元素上（和用户自己的指针吸附是同一个算法），而这里的统计没有做吸附。例如"该点哪个按钮"这一题，带适配器的模型回答正确，点落在"重试"按钮下方 9 像素处，按这里的标准算没指对，在应用里则会吸附到按钮上。
- **它也会答错**。同一次运行里，"我不想重试了，应该点哪里？"它答成了"点这里的「重试」"；Windows 上"哪个季度最高"答成了第一季度。
- 这张测试页的界面类型（对话框、价格卡片、表格、代码）和训练数据是同一类，只是内容和版式不同，所以它对应的是 3.1 节里"见过的类型"那一行，不能当作没见过的界面上的成绩。量化加真实渲染之后，指对的比例从离线评测的 94% 降到这里的 50–63%（8 题）。
- 内存：带适配器时问完 8 题后 1.2 GB（Windows）、1.6 GB（Linux）、1.7 GB（macOS），和不带适配器时相当。
- 第 12 次运行重复了同样的对比，结果一致：带适配器 Windows 6.5 秒（指对 4 题）、Linux 6.5 秒（5 题）、macOS 12.5 秒（5 题）；原版精确定位 Windows 27.3 秒（5 题）、Linux 17.3 秒（5 题）；原版快速定位仍然是 0 题。
- **绝对耗时取决于那一次分到的机器**。CI 第 13 次运行（模型和代码路径没有变）整体快了一倍多：带适配器 Windows 2.9 秒（指对 4 题）、Linux 3.9 秒（5 题）；原版精确定位 Windows 10.7 秒（5 题）、Linux 12.5 秒（5 题）；原版快速定位还是 0 题。同一次运行里 macOS 反而更慢（17.8 秒，5 题）。所以三次运行合起来只能说：带适配器每题约 3–7 秒，是同一台机器上精确定位的三分之一到四分之一；指对的题数三次都是 4–5 题。宣传材料里的"约 7 秒""17–25 秒"取的是第 11 次运行，是三次里较慢的一组。

## 4. 安装、指向模式和办公动作在三个系统上的检查

来源同第 2 节（第 9 次运行）。

| 检查项 | Linux | macOS | Windows |
|---|---|---|---|
| 读出资源管理器里选中的文件（对着真实的资源管理器窗口，含中文文件名） | 不适用 | 没有测 | ✅ 第 11、12 次运行；改写后（支持标签页、桌面）的版本：第 13 次运行 |
| 应用自己下载运行时和模型并校验 SHA-256 | ✅ | ✅ | ✅ |
| 本地模型启动、回答问题 | ✅ | ✅ | ✅ |
| 指向模式一个来回：截屏、叠加层盖住整个屏幕并拿到焦点、钉住一块、退出 | ✅ 进入 0.25 秒 | ✅ 进入 0.98 秒（第 11 次运行里因为启动慢没有通过，见下） | ✅ 进入 2.1 秒 |
| 办公动作全套（合并 PDF、做 PPT、Word 排版与转换、文字排版），结果重新打开核对 | ✅ | ✅ | ✅ |
| 后加的办公动作（共 33 个）：每个模块逐项核对（Linux）；文档、表格模块逐项核对，外加全部动作在 23 种选中情况下各跑两遍、确认原文件不变且不覆盖（三个系统） | ✅ 第 14 次运行 | ✅ 第 13 次运行 | ✅ 第 13 次运行 |
| 完整交互（真实鼠标键盘：悬停、右键固定、点选项、追问、选中文字弹出动作…） | ✅ 25 步 | 没有测 | 没有测 |

macOS 和 Windows 的"指向模式"检查是程序自己调用进入和退出，没有人或脚本真的去移动鼠标、按热键；完整的鼠标键盘交互只在 Linux 上自动化测过。

第 13 次运行里 Linux 的完整交互测试在第 24 步失败过一次（第 14 次同一步通过）：面板没有弹出来。没有复现到；从代码看最可能的原因是：点完面板上的按钮后，叠加层还占着键盘焦点，紧接着报告的"选中了文件"被当成"在指点自己的窗口里选了字"而忽略。现在只对选中文字做这个判断，文件不再受影响；改后本机重跑 25 步通过，但这不能证明原因就是它。

第 11 次运行里 macOS 的指向模式检查没有通过：应用刚启动、叠加层页面还没加载完就进入了指向模式（当时只等 5 秒）。等待上限改为 30 秒之后，CI 第 12 次运行里三个系统全部通过（macOS 进入 0.86 秒，Windows 2.9 秒，Linux 0.17 秒）。
